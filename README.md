# BaiyuTitle

Minecraft Paper 服务器的称号插件。多称号展示、条件组合购买、玩家间交易、称号组与羁绊、兑换码、管理端编辑器与 PlaceholderAPI 集成。

面向 Paper 1.21.11 及以上（Purpur 可用），JDK 21。

---

## 关于开发方式

这个项目的代码由 AI 编程助手完成。写在最前面是因为从提交粒度、注释风格和测试密度都能看出来，藏着没有意义。

需要说明的是它不是什么：**不是「描述需求 → 拿到代码」的一次性产物**。

实际过程是：

1. 先把业务规则写成 954 行的设计文档，把每种边界情况的行为定下来，再动第一行代码
2. 架构约束先于实现——单类 250 行上限、禁止静态单例、领域层不依赖服务端 API、玩家可见文本必须走语言文件
3. 分十个阶段推进，每个阶段结束跑完整构建，上一阶段不通过就不进下一阶段
4. 每个阶段完成后做一次评审，发现的问题要么当场修掉，要么记进待办并写明为什么暂时不修

AI 承担的是「按约束把设计翻译成代码」。技术选型、边界判断、验收标准由人定。换句话说，这个仓库的质量下限来自约束，不来自模型。

## 功能

**称号展示**

- 多个称号同时展示，数量由玩家组决定（默认普通玩家 1 个、VIP 3 个，可在配置里加组）
- 每个栏位可以是固定称号，也可以从自选池里随机
- 支持聊天栏前缀、可选写入 Tab 列表
- 悬停显示稀有度

**获取方式**

- 五种条件自由组合：免费、金币（Vault）、称号币、物品、权限
- 条件之间支持 AND / OR 两种组合；多个分支同时满足时由玩家选择付款方式
- 支持限时限量、按组限定、活动窗口

**玩家间交易**

- 报价列表、报价详情、历史记录
- 交易期间不锁定称号，允许多单并存，成交时全量复核，先成交者得
- 报价 72 小时后自动过期

**组织与收集**

- 称号组：成员由权限自动同步，入组授予、离组收回
- 羁绊称号：集齐所需称号后自动授予，失去条件不回收
- 兑换码与称号卡
- 自定义称号：四种付款方式任选，铁砧界面输入名称

**管理端**

- 19 项称号编辑器（价格、购买类型、可见性、稀有度、简介、条件、羁绊需求等）
- 玩家仓库查看与收回、购买者列表、全服交易日志

**集成**

- PlaceholderAPI：20 余个变量（余额、各类持有数、栏位上限、当前佩戴预览等）
- 6 个对外事件，其中 2 个可取消，供其他插件拦截购买与交易

## 架构

```
api       对外事件与接口，不依赖其他模块
common    领域模型 + 数据访问 + 业务服务，不依赖服务端 API
paper     服务端实现、命令、菜单、监听器
```

依赖方向单向：`paper → common → api`。

`common` 模块不 import 任何 `org.bukkit` 类型，因此领域层的两百多个测试不需要启动服务器，毫秒级跑完。这是整个项目可测试性的基础。

业务对象全部经构造器注入，唯一的组合根是 `paper` 模块的 `bootstrap/PluginAssembly`。没有静态单例，所以不存在重载后持有一份过期引用的问题。

## 构建

需要 JDK 21。Gradle 由 wrapper 提供。

```bash
./gradlew build              # 编译 + 测试 + 产物完整性校验
./gradlew :common:test       # 只跑数据层（H2 与 SQLite 各跑一遍）
./gradlew :paper:test        # 只跑表现层纯函数测试
./gradlew :paper:runServer   # 起测试服，自动下载 Vault 与 PlaceholderAPI
```

产物在 `paper/build/libs/`。文件名带 `sources` 或 `javadoc` 的不是运行包。

## 使用

```
/byt                    打开装扮菜单
/byt shop               打开商店
/byt open               打开仓库
/byt trade              交易报价列表
/byt redeem             输入兑换码
/byt reload             重载配置与语言文件（需权限）
/byt admin              管理菜单（需权限）
```

| 权限 | 默认 | 说明 |
|---|---|---|
| `baiyutitle.use` | 所有玩家 | 基础使用 |
| `baiyutitle.command` | 所有玩家 | 命令入口 |
| `baiyutitle.command.help` | 所有玩家 | 帮助 |
| `baiyutitle.trade.create` | 所有玩家 | 发起交易 |
| `baiyutitle.admin` | OP | 管理与编辑 |
| `baiyutitle.command.coin.others` | OP | 调整他人称号币 |

分组栏位上限通过组权限决定，默认组 `baiyutitle.group.vip` 给 3 个栏位。

## 几个实现细节

**数据库测试跑的是真迁移。** H2（MySQL 模式）与 SQLite 各跑一遍完整的 Flyway 迁移，不是 mock 出来的表结构。方言差异用构建期的迁移文件合并解决，所以 `CREATE INDEX` 这类语句在两边都能执行。

**售罄靠条件 UPDATE，不靠先查后写。** 扣减库存是 `UPDATE ... WHERE sold_count < cap`，影响行数为 0 即视为售罄，并发下不会超卖。

**防止重复持有靠索引，不靠应用层判断。** 三列唯一索引加一个可空的 `active_marker` 列——NULL 不参与唯一约束比较，只有 ACTIVE 状态的行填 `TRUE`。这样同一玩家对同一称号最多一条有效持有记录，历史记录不受限制。

**线程边界是硬约束。** 数据库操作只在单写线程与小读池执行，服务端 API 只在主线程调用，运行时断言线程归属。混用会立刻抛异常，而不是等到数据不一致才发现。

**聊天路径零数据库查询。** 聊天渲染与 PlaceholderAPI 变量只读内存快照，不触碰数据库，避免发言频率高时成为瓶颈。

## 已知限制

- **不支持 Folia。** 区域化调度需要重写整个表现层，收益不抵成本。
- **不显示头顶称号。** 只能用记分板队伍前缀实现，会与记分板、前缀、TAB 类插件争抢队伍归属，所以只写入 Tab 列表。
- **菜单布局写死在代码里。** 不支持 yml 自定义布局；文案可以改（语言文件），布局不行。
- **业务设计文档与开发记录不随仓库发布。** 仓库只放代码，设计文档保留在本地。
- **部分类超过自己定的 250 行上限**，最长的一个 580 行，属于已知遗留，后续拆分。
